# Visual Search Task

This Python code is based on a famous psychology experiment: the visual search task. This task typically requires the participant to locate and identify a “target” item among a number of “distractors.” The task measures response time and benefits from tracking eye movement or cursor placement to see how long it takes the participant to find the target and at what accuracy. The basic task is usually conducted with letters (like L’s and a T) or colors (red dots and a blue dot). For this code, however, we expanded upon this basic structure by incorporating images. Referencing the popular book series Where’s Waldo?, we emulated those search tasks with an image of Waldo, manipulating his environment in each condition. To run the experiment, open up the “search_task.psyexp” file and click “run pilot”. To view the data of the experiment, look in the “data” folder for a document called “pilot_animal_words_[date/time].log”.

In this project, we successfully created our own search task experiment with distinct trials and a way of measuring the response times and cursor tracking. One of our biggest struggles was actually understanding the PsychoPy toolbox and this transition from MATLAB. It had taken us quite a bit to get acclimated to MATLAB in the first place, after all. To ease this transition and get used to using the PsychoPy Builder, we watched tutorials and actually followed along with them (which is incidentally why some files may still reference “animal_words”, the experiment from the tutorial). Through creating this separate experiment we gained a better understanding of the different stimuli like Image and Mouse. 

Once we got the first trial done, we knew the next ones would be much easier since we’d figured out how to create the structure. We decided that we could make a trial with Waldo wearing only white and red and another with a different-colored candy cane—this way we could measure the effects of color and item type on response time. 

One “aha!” moment that we had was discovering that we could use code within the PsychoPy builder alongside the stimuli. As for the distractors, this allowed us to print 150 images of fake candy canes where we had previously worried we needed to make 150 separate stimuli per trial. We were also surprised to learn how seamlessly this worked alongside the stimuli blocks in the builder.

We struggled a fair amount trying to figure out how to incorporate the sound element. At first, we’d decided to add it to the same routine and find a way to use the Code stimulus to play the sound after the valid click. For whatever reason, this wasn’t working. After about an hour of troubleshooting, we realized we could just make it a separate action after the long routine which was successful; it just made the code a bit lengthier. Instead of making separate trial sections in the builder, we realize that we could have just reused the same and changed the conditions in the folder. While this would have made more sense, we thought it would be easier for us to debug and fix any visual issues if they had their own loops and routines. This did make it pretty tedious when adding in the demo routines, for example. In the future, we’d be interested in exploring how to better use conditions so this wouldn’t be necessary.

Working with PsychoPy Builder proved pretty difficult, especially with GitHub. We weren’t used to working with so many files, so it became a bit more difficult to keep track of everything and where they were. We ran into many issues with commits and pulling the files and especially running them on our separate computers.

We created and ran successful trials and planned to include the data collected from the players' trials in a results display at the very end of the experiment, but that proved difficult. When going into the code to edit the sequence and add to past lines, there were multiple errors, and when using AI tools to read the code and search for bugs, it would detect no issues, but PsychoPy could not run the code or crash. We spent several hours trying to code a final screen showing the results of the experiment, but it was ultimately unsuccessful. We tried to add in code to the trials to track the response time but ran into several problems which led to the experiment crashing completely. We did not think this was a terrible loss, considering the user can still view their data in the sheet after the experiment; though, we would love to know how we could have incorporated this successfully.

Overall, we were able to successfully create this experiment while adding our own fun twists and manipulations across trials. If we were to do this project again, we would prioritize finding a way to track data ahead of time so that we could plan the code around it as opposed to messing with our already-created code.
